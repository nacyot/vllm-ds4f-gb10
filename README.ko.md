# 긴 에이전트 세션 여럿을 상시 메모리에 유지하기: 멀티노드 vLLM 디스크 KV 오프로딩

**목표.** 긴 에이전트 세션 여럿을 한꺼번에 돌리면서, 세션의 KV 캐시가 만료될까 걱정하거나 수 분짜리 프리필을 다시 물지 않는 것. 통합 메모리를 가진 GB10 DGX Spark 두 대에서 이는 40만 토큰 이상 세션을 다섯 개 이상 상시 메모리에 두고 즉시 전환하며, 밀려난 과거 세션도 재프리필 전체 비용 없이 되살리는 것을 뜻한다. 이 작업이 겨냥한 표적이 이것이고, 복원 시간 단축을 포함한 나머지는 전부 이 목표를 위한 수단이다.

이건 [vLLM](https://github.com/vllm-project/vllm) 0.27.1 위의 실험적 패치 모음이다. 특정 구성(DGX Spark GB10 두 노드, 통합 메모리, DeepSeek V4 Flash FP8, 두 노드에 걸친 텐서 병렬)을 겨냥한다. 레퍼런스 구현이지 프로덕션 보증이 아니다. 비슷한 환경을 돌린다면 아래 내용이 옮겨질 것이고, 아니라면 사례 연구로 읽으면 된다.

저자: nacyot.

## 문제

LLM을 긴 세션으로 셀프호스팅할 때 진짜 비용은 디코드 처리량이 아니라 재프리필이다. 50만 토큰짜리 에이전트 세션이 GPU 캐시에서 밀려나면, 다음 턴을 보내는 순간 서버는 대화 전체를 처음부터 다시 계산한다. 프리픽스 캐시가 빗나가면 어텐션 키와 값을 다시 짓기 위해 대화 전체를 다시 훑기 때문이다. 이 하드웨어에서 그 재프리필은 분 단위로 들어간다. 한 응답에 몇 분을 기다리는 건 사실상 단일 세션만 쓰라는 강요다.

그래서 로컬 에이전트의 병목은 초당 토큰이 아니라 살려 둘 수 있는 세션 수다. GPU 메모리는 유한하므로 세션이 여럿이면 가장 오래된 것이 밀려나고, 그걸 다시 여는 건 재프리필 전체다. 이게 전체의 근본이다. 메모리에서 밀려난 KV는 그냥 유실되고 메모리 계층 어디에도 남지 않으므로, 다음 접근의 재프리필은 메모리 안에서는 결코 피할 수 없다. 유일한 지렛대는 밀려나기 전에 KV를 어딘가 영속 저장에 써두는 것이다. 이건 GPU 안에서만으로는 풀리지 않는다.

KV 캐시는 토큰의 결정적 함수이므로 깔끔한 답이 있다. 밀려날 때 디스크에 쓰고, 세션을 다시 건드릴 때 읽어 와서 재계산을 건너뛰는 것이다. GPU에서 다시 짓는 데 435초가 걸리는 469k 토큰 세션의 KV는 디스크에서는 수 GB짜리 파일이고, 1GB/s 스토리지라면 몇 초 거리다. vLLM 0.27에는 실제로 티어링 경로(GPU 풀에서 CPU 버퍼를 거쳐 백엔드 스토리지로)가 들어 있다. 문제는 이것이 2노드 구성에서 동작하지 않았다는 점이다.

### 구성, 그리고 통합 메모리의 함정

- 하드웨어: DGX Spark 두 대(GB10, 각 128GB 통합 메모리), 200G 직결, 두 노드에 걸친 텐서 병렬.
- 모델: DeepSeek V4 Flash, FP8, 희소 어텐션 인덱서 포함.
- 엔진: 소스를 인라인으로 패치할 수 있게 venv에 설치한 vLLM 0.27.1.
- 디스크: 두 노드에 CIFS(`hard,retrans=6`)로 마운트된 8TB 캐시 볼륨, 실측 1GB/s.
- dspark 계열 드래프터로 추측 디코딩(디코드 약 1.5배).

GB10 통합 메모리는 이 거래를 미묘하게 만든다. GPU와 CPU가 같은 128GB를 나눠 쓰므로 "KV를 CPU RAM에 오프로드한다"는 통상의 전략이 제로섬이다. RAM에 준 만큼 GPU 풀이 줄어든다. 최종 설계는 RAM을 저장소가 아니라 GPU와 디스크 사이의 하역장(스테이징 버퍼)으로 다룸으로써 이를 반영한다. 이 관점 전환이 전체의 뼈대다.

## 무엇을 구현했는가: packed canonical 오프로딩

업스트림 티어링이 2노드에서 깨지는 지점은 저장 계층의 메모리 모델이다. vLLM의 CPU 캐시 티어는 `/dev/shm`의 mmap인데, 2노드에서는 같은 이름의 mmap이 노드마다 서로 다른 물리 메모리다. 헤드 노드가 저장 파일을 쓸 때 워커 랭크에 해당하는 절반은 채워지지 않고, 복원 시 그 0바이트가 GPU에 올라가 어텐션을 오염시킨다. 저장 파일을 부검하니 모든 파일의 정확히 절반이 0이었다.

수정 전에 방법론 하나를 짚는다. 실제로 시간을 잡아먹었기 때문이다. 복원 실험은 무관한 신선 세션 대조를 포함해야만 "통과"다. 복원된 세션 자체는 반쯤 깨진 캐시로도 그럴듯한 출력을 낼 수 있으므로, 복원 직후에 완전히 새로운 무관한 세션을 열어 서버 전체가 오염되지 않았는지 확인해야 한다. 초기 실행들은 이 대조를 건너뛰어 반쪽 성공을 성공으로 착각했다.

수정은 우회가 아니라 원천 제거다. 네 부품이고, 전부 env 게이트 뒤에서 opt-in이다.

**1. Canonical packed 레이아웃.** 각 랭크는 자기 데이터만 신뢰하고, 저장 시점에 모든 랭크가 정본(canonical) 레이아웃으로 완전한 사본을 쓴다. 반쪽 mmap 문제가 우회가 아니라 저장 포맷 수준에서 사라진다. 이는 MLA와 슬라이딩 윈도우 KV 그룹이 텐서 병렬 랭크 간에 복제된다는 사실에 기댄다.

**2. 그룹 슬라이스 압축 저장.** 초기 저장은 모든 블록을 1MB 슬랩 통짜로 써서 저장 밀도가 토큰당 148에서 177KB였고, 50만 세션 하나가 80GB를 넘었다. 레이어별 그룹별로 실제로 의미를 담는 바이트 수를 등록하고 그만큼만 디스크로 슬라이스하자 밀도가 토큰당 약 13KB로 12배 줄었다. 이제 50만 세션은 약 6GB다.

**3. 워커 직접 pread 복원.** 복원 시 헤드가 파일을 읽어 네트워크로 뿌리는 대신, 각 워커가 공유 스토리지에서 자기 슬라이스를 직접 읽는다. 승격되는 각 키에 (경로, 오프셋, 길이) 트리플이 실리고, 워커가 그걸로 자기 mmap을 채운다. 이것이 2노드 복원의 핵심이다.

**4. 방향별 스왑 경로 분리.** GPU와 스테이징 사이 복사는 방향마다 다른 커널을 쓴다. 강등(GPU에서 스테이징으로 쓰기)은 배치 복사 경로, 로드(스테이징에서 GPU로 읽기)는 Triton 커널이다. 한 경로로 대량 배치를 제출하면 Blackwell 드라이버 프런트엔드가 무너졌고(대형 복원이 결정적으로 GPU를 죽이는 깨끗한 이분 경계로 드러났다), 방향별 분리가 이를 피한다.

**5. TP 브로드캐스트 릴레이 복원 (opt-in).** 워커 직접 pread는 모든 랭크가 저장 파일에 닿을 수 있다고, 즉 공유 스토리지를 전제한다. 대안 경로는 한 랭크(TP 로컬 0번)가 canonical 파일을 읽어 나머지 랭크로 텐서 병렬 프로세스 그룹을 통해 브로드캐스트한다. KV가 랭크 간 복제이므로 한 번 읽으면 충분하고, 그래서 그 한 노드에만 스토리지가 있으면 되며 나머지는 빠른 상호연결로 복사본을 받는다. 이로써 저장 위치가 자유 선택이 된다. 단일 노드 내장 NVMe, 직결 디스크, 네트워크 마운트가 모두 동일하게 동작하고, 모든 노드가 볼 수 있는 마운트가 필요 없다. 브로드캐스트는 고정 크기 윈도우(기본 256MiB)로 쪼개져 임시 GPU 스테이징 버퍼가 세션 크기와 무관하게 상한에 묶이므로, 대형 세션 복원도 통합 메모리에서 설정된 메모리 예산 안에 머문다. `DSPARK_RELAY_RESTORE`로 opt-in, 기본 off.

작은 수리 몇 개가 함께 실린다. 인덱서 캐시의 추측 디코딩 비대칭, 부분적으로 채워진 블록의 구멍 건너뛰기, 라이터 로테이션 반쪽 쓰기다. 전부 합쳐 약 700줄이고, 재설치 후 재적용할 수 있게 멱등 패치 스크립트로 묶었다.

이 파이프라인을 처음 돌렸을 때 복원 직후 GPU가 결정적으로 죽었다(Xid 13). 소프트웨어 가설 여덟 개를 하나씩 소거한 끝에 원인은 GPU 드라이버로 밝혀졌고, 드라이버를 올리자 증상이 사라졌다. 몇 시간을 들여 배운 교훈: 방금 바뀐 게 네 코드라 해서 네 코드가 범인인 건 아니다.

## 무엇을 테스트했는가

가장 중요한 성질부터. 클라이언트는 아무것도 몰라도 된다. OpenAI 호환 API로 같은 대화를 보내면 서버가 프리픽스 해시를 조회해 디스크 티어에서 KV를 찾아 GPU로 승격한다. 세션 id도, 복원 호출도, 클라이언트 측 상태도 없다. 469k 인증 실행의 서버 메트릭이 이를 증명한다. 재계산 토큰 0, 디스크에서 로드 3,627MB. 재프리필이었다면 로드 0MB에 계산 434초로 찍혔을 것이다.

세션을 강제로 축출한 뒤 재접근해 잰, 콜드 구축(재프리필) 대 디스크 복원:

여기 수치는 전부 약 1GB/s 공유 네트워크 스토리지 기준이다(왜 중요한지와 로컬 NVMe면 어떻게 달라지는지는 한계 절 참조).

| 세션 크기 | 콜드 구축(재프리필) | 디스크 복원, 초기 | 디스크 복원, 재작업 후 |
|---|---|---|---|
| 94k 토큰 | 61초 | 8.1초 | 재측정 안 함 |
| 188k 토큰 | 133초 | 12.6초 | 재측정 안 함 |
| 469k 토큰 | 435초 | 27.8초 | 약 9초 |

"초기" 열은 첫 동작 버전, "재작업 후" 열은 아래 "28초에서 9초로"의 복원 경로 재작업 뒤로, 381k 세션에서 25.5초에서 9.1초로 실측했다. 소형 세션은 stat 비용이 이미 작아 이득이 적으므로 재측정하지 않았고, 이득은 순차 존재확인이 지배하던 대형 세션에 몰린다. 재프리필 대비 배속은 세션이 클수록 커진다. 재프리필은 컨텍스트에 따라 가속되는데 디스크 읽기는 선형이기 때문이다. 재작업 후 469k 복원은 435초 재프리필 대비 약 48배다.

릴레이 경로(item 5), 단일 노드 로컬 NVMe, 동일한 강제 축출 후 재접근 방식:

| 세션 크기 | 로컬 NVMe 복원 |
|---|---|
| 76k 토큰 | 2.6초 |
| 352k 토큰 | 7.5초 |

- 읽지 않는 랭크의 디스크 입출력, 저장과 복원 모두: 0바이트.
- 457k 토큰 세션 4개 동시 상주: 그들 사이 전환 각 1.7에서 2.1초.

다만 디스크 복원은 흔한 경우가 아니라 드문 경우여야 한다. GPU 풀을 13GiB(약 251만 토큰)로 두면 약 37만 토큰짜리 세션 여섯 개가 GPU에 완전히 상주하고, 그들 사이 전환이 매번 1.6에서 1.8초에 들어온다. 일곱 번째, 즉 밀려난 세션만 디스크에서 돌아온다. 6세션 상주 인증에서 저장 실패는 0이었고 메모리 여유도 넉넉했다.

동시성도 확인했다. 두 세션을 축출하고 동시에 재접근하니 188k 세션 두 개가 13.4초와 20.4초에 돌아왔고, 합 2,900MB, 사고 0이었다. 내려가는 강등 쓰기와 올라오는 승격 읽기가 스테이징 버퍼를 깨뜨리지 않고 겹친다. 신선 세션 대조는 매 실행 통과했다. 복원 직후 무관한 세션을 열어도 출력이 정확하고 수락률도 온전했다.

### 28초에서 9초로: 복원 경로 재작업

그 첫 28초 복원의 내부는 뜻밖이었다. GPU 복사 자체는 0.18초로 전체의 1퍼센트 미만이었다. 지배 비용은 각 청크를 디스크에서 stat하는 존재 확인 배치였다. 한 번의 조회 라운드가 수천 개 파일을 순차로 stat했고, 콜드 CIFS stat이 건당 3.4ms라 그것만으로 15초였다.

비용이 읽기 대역폭이 아니라 조회의 순차성이라는 게 분명해지자 수정이 따라왔다. 존재 확인 stat을 16스레드로 병렬화하니 15초가 1초가 됐다. 원격 워커 읽기를 병렬화해 1초를 더 벌었다. 469k 콜드 복원이 25.5초에서 9.1초로, 2.8배 줄었다. 각 단계는 A/B로 확인했다. 읽기는 이미 스토리지 대역폭을 포화시키고 있어 팬아웃은 소용이 없었고, 순차 stat이 진짜 비용이라는 건 측정으로만 드러났다. 이 복원 경로 부품들도 env 게이트 뒤에서 opt-in이다.

## 레시피


추측 토큰은 7로 둔다. 메모리를 짜내려 낮췄더니 출력 분포가 왜곡됐고, 속도와 수락률만 믿고 출력 품질 검사를 건너뛴 게 실수였다. 그 원인(깨진 출력과 건너뛴 툴 호출)은 이후 3원 구성 비교로 못 박았고, 값은 정규 설정으로 되돌렸다. `GPUUTIL`은 0.75로 낮게 둔다. 웜 페이지 캐시가 부팅 시 GPU 메모리 검사를 깎기 때문이다.

## 검증: 복원이 진짜임을 증명하는 방법

KV 복원에 대한 주장은 실수로도 쉽게 가짜가 된다. 프리픽스 캐시 히트는 복원처럼 보이고, 웜 페이지캐시는 빠른 디스크처럼 보이며, 재계산은 복원과 같은 정답을 (느리게) 내놓는다. 검증 하니스는 그 구멍들을 막는다. 방법:

1. **세션은 니들로 찔러본다.** 각 세션은 고유한 결정적 필러 텍스트(약 450k~506k 토큰, 세션별로 달라 교차 프리픽스 히트가 없음)이고, 첫 문장에 고유 비밀 코드를 심는다. 재접근마다 그 코드를 묻는다. 정답이면 복원된 KV가 바이트 수준으로 충실하다는 증명이다.
2. **디스크 읽기는 가정이 아니라 계측한다.** 모든 프로브가 `vllm:external_prefix_cache_hits_total`과 `vllm:kv_offload_load_bytes_total`의 증분을 기록한다. "상주"란 디스크에서 **0바이트** 읽고 답한 것이고, "복원"이란 외부 히트가 프롬프트의 ~99%를 덮고 기가바이트가 읽힌 것이다.
3. **콜드는 진짜 콜드다.** 복원 시험은 양 노드 서빙 프로세스를 먼저 재시작해 GPU 풀과 스테이징을 비우고, KV의 유일한 출처를 디스크 티어로 만든다.
4. **재계산이 대조군이다.** 같은 세션을 처음부터 다시 지은 값이 복원을 판정하는 재프리필 기준선이다.

2026-08-27 수용 런 결과(약 506k 세션 6개 + 450k 세션 5개, 전 구간 니들 정답; 노드당 통합 메모리 ~120GB, GPU KV 풀 18GiB):

```

  상주 (RAM, 디스크 읽기 0)      #                        2~4초    라운드로빈 12/12
  파킹 (디스크에서 복원)          ####                     12~18초  3.5~3.9GB 읽음, 외부 히트 99%+
  재계산 (대조군)                ############################################  ~680초
```

```

  admission 게이트 수리 전        ############################################  45분  (1개 복원, 4개 재계산)
  수리 후                        ##                                            67초  (5/5 복원, 직렬 체인
                                                                                     19 → 33 → 47 → 60 → 67초)
```

```

  오프로딩 on                    ~660~694 tok/s
```

상주 용량은 부팅 로그의 비관적 "maximum concurrency" 지표가 아니라 실측 토큰당 할당(리텐션 체크포인팅 포함 ~5.2KB/token)을 따랐다: 약 500k 세션 6개가 18GiB 풀의 ~84%를 점유하며 전부 즉답하고, 7번째가 오면 가장 오래 안 쓴 세션이 디스크로 밀려나 다음 접근 때 12~18초 복원 1회를 치른다. 오프로딩을 켠 동시성 벤치(2.5k 토큰 프롬프트, out=512, temp 0.6): c8/c16/c32 수락률 1.58/1.45/1.43, 거부 레인 0, 집계 처리량 단조 증가. 즉 오프로딩 경로는 추측 디코딩을 건드리지 않는다.

프로브 스크립트는 작고(OpenAI 클라이언트 니들 하니스 + `/metrics` 증분) 이 트리 밖에 있다. 위 방법이면 이 포크의 어떤 배포에도 재현할 수 있다.

### 결함 주입 (2026-08-28)

로드 실패 배선은 저장소를 일부러 부수는 방식으로 검증했다. 오라클은 니들 세션이다:

```
청크 절단 (읽기 실패)       수리 전: 483초에 실패 로그 8,487줄, 요청 영구 대기
                            수리 후: 실패 로그 1줄 -> 재계산 43.8초, 니들 정확

프루너가 세션 밑을 지움      깨끗한 전량 MISS -> 재계산 76.3초, 니들 정확
```

"수리 전" 행 자체가 이번 라운드의 발견이다: 1차 배선이 스케줄러 쪽 라이브락(실패한 승격 키를 async lookup stat 캐시가 스텝마다 HIT로 재제공)을 드러냈고, 실패 키 포이즌 + 캐시 무효화로 다음 lookup이 확정 MISS가 되어 재계산으로 흐른다.

## 한계와 열린 문제

정직한 목록.

1. 약 500k 세션의 복원은 이제 13.8~16.1초다(릴레이가 청크당 중복 디스크 읽기를 제거). 그래도 상당 부분은 여전히 제어면에 묶여 있다. GPU 복사는 0.18초이고 나머지는 조회, 원격 읽기, 꼬리 재프리필, 토크나이즈에 흩어져 있다. 이론 하한은 대략 6에서 7초다. 더 내리려면 조회 범위를 좁히고 승격을 프리페치해야 하며, 근본적으로 진짜 답은 애초에 세션이 밀려나지 않도록 풀을 키우는 것인데 이건 하드웨어 규모 문제다.
2. (2026-08-30) 디스크 티어에 보존 정책이 생겼다. `DSPARK_TAIL_ONLY=2`면 체인은 프롬프트 앵커마다 창 스냅샷 1벌을 저장하고, `DSPARK_TAIL_KEEP=K`가 새 앵커 안착 후 체인의 최신 K개보다 오래된 경계의 스냅샷을 지우며, 외부 TTL 프루너(윈도 그룹 파일만, full-attention 청크는 절대 아님)가 버려진 체인을 정리한다. 전역 용량 상한은 여전히 외부 mtime 순서 프루너 몫이다. 그 전까지는 디스크 티어에 내장 용량 상한이나 GC가 없고, 외부의 mtime 순서 프루너가 용량을 관리한다. 이제 재저장 dedup과 로드가 mtime을 갱신하므로 그 프루너는 최초 저장 시각 기준 FIFO가 아니라 LRU로 동작하지만, 세션별 크기·마지막 접근을 색인하는 트리 내 GC는 여전히 미래 과제다.
3. (2026-08-30) anchor-now tail-only 저장(`DSPARK_TAIL_ONLY=2`)은 이제 검증됐고 기준 배치에서 켜져 있다: 450k 토큰 프리필이 창 스냅샷 16 GiB 대신 62 MiB를 쓰고, 101k 세션이 3.1초에 외부 전량 히트로 콜드 복원된다. 이전 회귀는 eagle extra-chunk pop(2026-08-27 수정)과 저장 측 게이트였고 둘 다 테스트로 덮였다.
4. 이 설계는 오래 사는 세션 여럿을 지속시키고 즉시 재접근하는 것을 최적화한다. 원 처리량과 빠른 세션 회전을 재접근 지연과 세션 지속으로 맞바꾸며, 이는 회전이 잦은 멀티테넌트 서빙과는 다른 표적이다.
5. 저장 계층은 두 노드가 모두 볼 수 있는 공유 스토리지를 전제한다. 복원 시 각 워커가 스케줄러 노드가 쓴 파일에서 자기 슬라이스를 공유 마운트를 통해 읽으므로, 노드별 로컬 디스크는 기본 지원되지 않는다. 여기 수치는 약 1GB/s 네트워크 캐시 볼륨 기준이라, 복원의 읽기 묶인 부분(9초의 약 절반: 존재확인 stat, 승격 읽기, 원격 읽기)은 SSD 속도가 아니라 그 링크에 묶인다. MLA KV가 랭크 간 복제이므로 한 복사본이면 충분하다. 릴레이 경로(item 5)는 한 랭크가 그 복사본을 읽어 나머지에 브로드캐스트하므로, 저장소가 한 노드의 로컬 NVMe, 직결 디스크, 네트워크 마운트 어디에 있어도 되고 노드별 공유 마운트가 필요 없다. opt-in이고 기본 off라, 끄면 기본 경로는 여기 설명대로 공유 마운트에서 읽는다.
6. 상시 출력 감사 게이트가 아직 없다. 두 출력 품질 회귀 모두 합성 프로브가 아니라 실사용에서 드러났다. 깨진 출력 스위프, 툴 호출 배터리, 잘린 툴 호출 시나리오를 상시 게이트로 만드는 것이 남은 일이다.

7. 워커 측 로드 오류가 아직 `get_block_ids_with_load_errors`로 배선되지 않아, 설정된 `kv_load_failure_policy=recompute`가 읽기 실패에서 발동하지 못한다. 현재 완화는 스테일 바이트를 조용히 통과시키는 대신 요란한 에러와 zero-fill이다. 보고 배선이 다음 정확성 과제다.
8. native DeepGEMM 인덱서 로짓 경로는 호출마다 exact-size 출력을 할당한다. 폭이 변하는 프리필 churn에서 이것이 할당자 예약 메모리를 랫칫시킨다(A/B 실측: 워커 측 완만한 증가의 약 70%). native 경로용 버킷 재사용 출력 버퍼가 예정된 수리다. Triton 경로에는 이미 있다.

이 포크는 실험적인 것으로 다뤄라. 2노드 통합 메모리 홈랩에서 디스크 KV 오프로딩을 실측까지 밀어붙인 레퍼런스이지, 프로덕션에 그대로 넣는 물건이 아니다.

마지막 방법론 하나. 이 작업의 대부분 사건은 "판별 실험 하나가 가설 열 개를 이긴다"로 압축된다. 반쪽 mmap 오염은 신선 세션 대조로, 이른 캐시 축출은 GPU 히트와 디스크 복원 측정 분리로, 출력 왜곡은 3원 비교로, 복원 병목은 단계별 측정으로 가려졌다. 증상을 읽고 가설을 세우되, 다음 행동은 언제나 그것을 하나로 좁히는 실험이게 하라.

## 이 포크의 다른 opt-in 노브

위 오프로딩 레시피 외에도 이 트리에는 실험적 env 게이트 변경이 몇 개 더 있다(전부 기본 off):

- **복원 경로 병렬화**("28초에서 9초로" 참조): `DSPARK_FS_LOOKUP_THREADS`, `DSPARK_FS_LOAD_TASKS`, `DSPARK_FS_STORE_TASKS`, `DSPARK_FS_PREAD_THREADS`, `DSPARK_FS_PREAD_WINDOW`, `DSPARK_FS_PREAD_SKIP`.
- **건별 KV JSONL 로그** 복원/저장 에피소드 오프라인 분석용: `DSPARK_KV_EVENT_LOG=/path/file.jsonl`.
- **TP 브로드캐스트 릴레이 복원** 한 노드에만 저장 파일이 있으면 되게 함(한 랭크가 읽어 TP 그룹으로 나머지에 브로드캐스트, 저장 위치가 자유 선택): `DSPARK_RELAY_RESTORE=1`. 브로드캐스트 윈도우 크기: `DSPARK_RELAY_WINDOW_BYTES=268435456` (256MiB).
- **DeepSeek V4 툴 호출 생성 안정화**(실험적, 검증 진행 중): `DSPARK_SPEC_OFF_GUIDED`(툴 요청을 추측 디코딩 문법 검증에서 제외), `DSPARK_DSML_LEAK_GUARD`(툴 호출 마크업 토큰이 본문으로 새면 요청 중단), `DSPARK_TOOL_TEMP0`(구조 토큰이 결정적이도록 툴 턴에 temperature 0 강제).
- **GB10 커널과 백엔드 노브**: opt-in B12X MXFP4 MoE 백엔드, mHC 프리놈 경로용 DeepGemm opt-in, Triton 경로용 e8m0 블록 스케일 업캐스트, DSpark 드래프트 어텐션 백엔드 고정, MLA 인덱스 폭 라운딩.

- **할당기 랫칫 수리 (2026-08-28)**: `VLLM_SM12X_DG_ALLOC_BUCKETS`(네이티브 SM120 mqa-logits 경로의 버킷 로짓 워크스페이스 재사용, 기본 켜짐, `0`이면 기존 정확 크기 할당), `VLLM_SM12X_DG_ALLOC_LOG`(N콜마다 reserved 바이트·할당 카운터 로그, 기본 꺼짐).
- **동시성 하의 복원 견고성** (2026-08-27): `DSPARK_RESTORE_CONCURRENCY`(승격 admission 게이트, 기본 1), `DSPARK_PRIMFULL_RETRIES`(스테이징 만석을 MISS로 붕괴시키는 대신 재시도할 지속 초, 기본 300), `DSPARK_SWA_RESERVE`(슬라이딩 윈도우 꼬리 승격 몫을 남겨 초과 세션이 맞는 프리픽스만큼 복원), `DSPARK_FINISH_STORE_RETRIES`(파킹 시 꼬리 저장 재시도, 기본 30).
- **스테이징 mmap 위치**: `DSPARK_OFFLOAD_MMAP_DIR`(CPU 스테이징 mmap을 tmpfs 대신 디스크 파일로, `posix_fallocate` 선할당), `DSPARK_OFFLOAD_PIN`(호스트 등록 정책, 디스크 백업이면 기본 미핀).
- **릴레이 직접 브로드캐스트**: `DSPARK_RELAY_DIRECT`(파일 재읽기 대신 스테이징 mmap에서 TP 브로드캐스트, 기본 on; 폴백 pread는 길이 검증).
- **스케줄러 admission**: `DSPARK_ADMIT_RESERVED`(fresh admission에도 인플라이트 프리필 예약 반영, 기본 on), `DSPARK_PPCAP`(동시 compute-prefill 상한).
- **fs 티어 위생**: `DSPARK_SIDECAR_STRICT`(레이아웃 사이드카 파싱 실패를 무성 포맷 전환 대신 요란한 실패로), `DSPARK_FS_PROMOTED_KEYS_CAP`(LRU 바운드), `DSPARK_LOOKUP_TRACE`(primary 만석 miss와 진짜 miss 구분).

- **창 스냅샷 정책 (2026-08-30)**: `DSPARK_TAIL_ONLY=2`(anchor-now: 슬라이딩윈도 그룹은 프롬프트의 마지막 full-attention 정렬 경계 직전 w(+e) 청크만 저장), `DSPARK_TAIL_CKPT_TOKENS`(긴 프리필 중 주기 안전 체크포인트, 선택), `DSPARK_TAIL_KEEP=K`(체인별 보존: 새 앵커 저장이 완료되면 최신 K개보다 오래된 정렬 경계의 스냅샷을 삭제, KV JSONL 로그에 `prune` 이벤트).
- **추론 루프브레이커 (2026-08-30)**: `--reasoning-config '{"loop_break_max_pattern_size":128,"loop_break_min_pattern_size":8,"loop_break_min_count":4,"loop_break_min_reasoning_tokens":512,"loop_break_check_interval":16}'`로 스케줄러 측 정확 반복 감지(추론 구간 한정)를 켠다. 판정은 `SchedulerOutput`으로 워커에 전달되고, 워커는 그 요청의 thinking 예산을 낮춰 기존 V2 강제 커널이 추론 종료 시퀀스를 내보내게 한다(답변은 계속). 요청별 옵트아웃 `thinking_loop_break: false`. `DSPARK_DEFAULT_THINKING_BUDGET=N`은 클라이언트가 `thinking_token_budget`을 생략했을 때 서버 기본값을 적용한다(요청에서 `-1`이면 해제). 둘 다 구간당 한 번 로그.
- **SM120 디코드 타일링 (2026-08-30)**: `DSPARK_SM120_DECODE_TILE=64`(기본)가 DSpark verify 배치를 64행 이하 FlashInfer 러너 호출로 잘라 항상 독립 디코드 커널을 타게 한다. `0`이면 종전 통짜 호출.

이들은 각 커밋 메시지에 문서화돼 있다. 이 저장소는 실험을 계속 쌓아 나갈 것이다.

## 변경 이력

### 2026-08-30 — 스냅샷 보존, 추론 루프브레이커, 디코드 타일링 (4커밋)

- **창 스냅샷이 디스크를 채우던 것을 막았다.** 티어 655 GiB 중 92%가 프리필이 4096토큰 경계를 지날 때마다 쓰던 슬라이딩윈도 상태 스냅샷이었고(업스트림 v0.28 의미론, 버그 아님) 복원은 마지막 1벌만 읽는다. `DSPARK_TAIL_ONLY=2`를 기준 설정으로 채택(450k 프리필: 스냅샷 16 GiB → 62 MiB)하고 `DSPARK_TAIL_KEEP=K`가 새 앵커 안착 후 체인의 옛 스냅샷을 지운다. 리뷰로 걸러낸 가드: full-attention 청크는 절대 대상 아님, 삭제 시 promoted/poison 장부 불변(rank>0가 미충전 스테이징을 읽게 됨), 창이 세그먼트보다 넓으면 범위 클리핑. 버려진 체인은 외부 TTL 스크립트. 테스트베드 검증: 101k 세션 콜드 복원 3.1초·외부 히트 98,304토큰, prune 이벤트가 직전 앵커의 5파일만 정확히 삭제.
- **Model Runner V2용 추론 루프브레이커.** vLLM PR #52677은 V1 thinking-budget 홀더에 있어 DSpark(V2)와 함께 못 돈다. 권위 있는 출력 토큰 id 위에서 스케줄러 측 감지(`check_sequence_repetition`, 추론 구간 한정)로 이식하고, 판정을 `SchedulerOutput`에 실어 V2 `ThinkingBudgetState` 강제 커널로 적용했다. 이 과정에서 V2 예산 기계가 배선되지 않은 것(샘플러에 `reasoning_config` 미전달, 로짓 처리 게이트에 예산 항 부재, natural end 마커 id 부재, 인입 단계 거부)을 발견해 모두 고쳤으므로 이 스택에서도 `thinking_token_budget`이 작동한다. 라이브: 유도한 루프는 추론 2천~4천 토큰에서 끊기고 답변이 이어지며, 열거 대조군은 발화하지 않는다.
- **DSpark verify 배치를 64행 이하로 타일링.** FlashInfer sparse-MLA 러너는 쿼리 64행 초과를 prefill 오케스트레이터로 보내는데, SM121에서 확률적으로 교착하고(mia #141, flashinfer #3700/#4732) split-K 스크래치를 매 스텝 재할당한다. 16 시퀀스 × (5+1)이면 바쁜 스텝마다 96행이었다. `_forward_decode`가 워밍업 때 예약한 스크래치를 재사용하며 64행 슬라이스를 반복 호출한다. 테스트베드 96행 A/B: 합산 비용 3~5%, 오류 0. 4노드 TP=4 배치는 16 시퀀스를 유지.
- **인덱서 숏컷 캡처 가드**(vLLM #52492): 짧은 문맥용 "후보 전부 선택" 숏컷을 CUDA 그래프 캡처 중에는 건너뛰어, 긴 프리픽스 캐시 히트 후 재생이 점수 없는 후보를 고르지 못하게 했다.
- 운영 계층(이 트리 밖): 통합 메모리 노드의 기동 전 메모리 컴팩션(파편화된 UVM 메모리가 18 GiB KV 할당을 20분 넘게 멈춤, `compact_memory`로 1분 안에 해소, `vm.compaction_proactiveness=100`으로 재발 방지), 워치독 부팅 유예 720 → 1500초, venv 전용 라이브 패치 10개 트리에 보전.

### 2026-08-28 — 신뢰성 라운드 (2커밋)

- **로드 실패의 끝-끝 재계산.** lookup 시점엔 존재하지만 읽기에 실패하는 청크(절단·프루닝·비행 중 unlink)가 assert 사망, zero-fill, 그리고 결함 주입이 드러낸 스케줄러 쪽 라이브락(실패한 승격 키를 stat 캐시가 스텝마다 HIT로 재제공)으로 끝나던 것을 수리했다. 이제 블록별 읽기 실패가 보고되고, 실패 키는 포이즌되며, async lookup 캐시가 무효화되어 다음 lookup이 확정 MISS → 해당 구간 재계산. store 실패는 fail-stop 유지(저장됨으로 오기록 금지). 하이브리드 그룹 zip 가드로 블록 테이블 무성 절단도 차단.
- **네이티브 DeepGemm 로짓 워크스페이스 유계화.** SM120 mqa-logits 경로가 KV 길이를 기하 사다리로 올림해 상주 워크스페이스의 제로카피 뷰로 로짓을 서빙한다(폴백은 버킷 버퍼 소형 LRU, DBO ubatch 스레드는 캐시 우회). 혼합 길이 프리필의 예약 메모리 랫칫을 제거.
- 운영 계층(이 트리 밖): 페어 pre-start가 랙 전체 재부팅 후 start limit을 태우는 대신 상대 노드를 기다리고, 워치독이 장기 activating 고착을 감지하며, 새 대기 예산에 맞춰 기동 타임아웃을 상향.

### 2026-08-27 — 하드닝 라운드 (19커밋)

- **동시 콜드 스왑인: 45분 → 67초.** 셋이 전부 필요했다: 한 번에 N개 요청만 fs→스테이징 승격을 개시하는 복원 admission 게이트; 디스크에 파일이 실재하고 스테이징만 만석일 때 MISS 대신 재시도(잔재 붕괴 경로: 앞 복원의 로드가 스테이징을 핀 중일 때 차례를 받은 요청이 하이브리드 복원 전체를 버리고 재계산으로 갔다); 그리고 키당 예산이 조회 패스 한 번에 소진됨을 실측으로 잡은 뒤의 시간 기반 재시도 예산.
- **릴레이 복원이 스테이징에서 직접 브로드캐스트**(승격 계약상 바이트가 거기 상주함이 보장됨) — 복원 경로 디스크 읽기 절반, 500k 복원 16~32초 → 13.8~16.1초. 남은 pread 경로는 읽기 길이를 검증하고 요란하게 오염 표시한다.
- **admission이 인플라이트 프리필 예약을 계산**(이전에는 async 로드 admission만) — 대형 프롬프트 N개가 과잉 admit 후 preemption 스래시로 가는 대신 용량 크기 웨이브로 들어온다.
- **파킹 시점 저장 재시도** — 요청 종료 순간 스테이징이 만석이어도 파킹 세션의 꼬리 청크를 조용히 버리지 않는다.
- **스테이징 mmap 수명주기**: env로 디스크 백업 선택(통합 메모리에서 노드당 tmpfs ~12GB 해방), `posix_fallocate`로 ENOSPC가 오프로딩 중 SIGBUS 대신 깨끗한 기동 오류가 되게, 디스크 백업이면 기본 미핀.
- **콜드 복원 reserve 캡**: 초과 세션이 전량 재계산으로 붕괴하는 대신 스테이징에 맞는 프리픽스만큼 복원.
- **fs 티어 하드닝**: 재저장 dedup·로드의 mtime 갱신(외부 LRU 프루너가 최초 저장 시각을 보고 가장 뜨거운 청크부터 지웠다), per-block 배치 검증, short-read 증거가 있을 때만 unlink(fd 고갈이나 O_DIRECT EINVAL이 정상 캐시 파일을 지우지 않음; C 확장도 재빌드), 사이드카 실패의 strict 처리.
- **Eagle extra-chunk pop**이 내부 복원 경계를 전량 재계산까지 끌어내리지 않음(추가 청크가 실제로 히트했을 때만 pop).
- 기타: `_fs_promoted_keys` LRU 바운드, env 게이트 조회 트레이스, venv 수기 패치로만 존재하던 라이브 기능 트리 보전(`DSPARK_PPCAP` admission 캡, tiering 메트릭 확장), fs_io 빌드 레시피.

### 2026-08-25/26 — SM120 어텐션 오버레이와 출력 품질

- GB10/SM12x용 빌드 불필요 Triton sparse-MLA 오버레이(jasl의 ds4-sm120-min-enable 계열 채택) + 워밍업/샘플링 서브시스템. 동시성 하의 FlashInfer sparse-MLA 프리필 스톨 수리.
