## 3. 해석

### 3-1. MoE 그룹 GEMM: 서로 다른 전문가 수가 비용이다

- 같은 토큰 두 스트림은 전문가 집합이 c1 과 같다. 블록 수는 그대로이고 블록당 행만 둘이 돼 호출당 +12~18 % 다.
- 다른 토큰은 블록이 거의 두 배라 호출당 ×1.6~1.7 이다. 커널이 `m_indices < 0` 블록을 건너뛰는 것(계획 2-2)과 맞는다.
- FC2 의 같은 토큰 증가(+18 %)가 FC1(+12 %)보다 큰 것은 FC2 입력 행이 FC1 출력(활성화 양자화 뒤)이라 행 수에 비례하는 일이 더 크기 때문으로 보인다. 결론에는 영향이 없다.
- 호출당 FC1+FC2 시간은 같은 토큰 854 µs, 다른 토큰 1,232 µs 로, 라우팅 몫이 378 µs 다. c1 한 스텝의 서로 다른 전문가를 30 개 안팎으로 보면 전문가당 약 13 µs 이고, 랭크당 전문가 가중치 약 5.2 MB 를 ~400 GB/s 로 읽는 시간과 같은 자릿수다. 전문가 수를 직접 세지 않았으므로 추정으로 남긴다.
- K3(한 스텝 어긋남)가 K3b(같은 스텝)보다 호출당 5 % 짧다(749 vs 791 µs). 비프로파일도 92.0 vs 94.7 ms, 계획 단계도 92.2 vs 95.3 ms 로 같은 방향이다. 두 코드 프롬프트는 함수 틀이 비슷해 위상에 따라 토큰 일부가 겹칠 수 있으나, 이번 범위에서 원인을 확정하지 않는다. 벤치 정의에서 이 흔들림(± 2 ms)을 고려하면 된다.

### 3-2. NCCL

- 같은 토큰에서도 전송이 +1.8 ms 늘어난다. 스텝당 호출 수(90 회)는 같고 토큰 수(6 → 12)만 두 배이므로 메시지 크기 몫이다.
- 랭크 대기는 코드에서 −0.2~+0.5 ms 로 작다.
- 산문(K4)만 대기가 3.4 ms 로 크다. 산문은 Engram 조회 커널이 랭크마다 0.5~1.9 ms 로 달라서다(콜드 페이지 GPU fault, #37 모드 2 에서 본 현상이 레이어 14 표의 배경 populate 가 늦을 때 모드 1 에서도 난다). 느린 랭크를 다른 랭크가 기다리는 몫이다.

### 3-3. Engram 표 대기 (이슈 본문 후보 1)

- 모드 1 은 레이어 1 표만 기다린다. 대기는 c1 3.05 ms 에서, 같은 토큰은 그대로(3.06), 다른 토큰은 5.13 ms 가 된다.
- 같은 토큰의 두 스트림은 n-gram 해시가 같아 읽을 표 페이지가 같고, 다른 토큰이면 페이지가 두 배다(#37 의 콜드 NVMe 읽기 한계).
- 산문은 5.97 ms 다.
- #37 결과 5 장의 후속 아이디어(모드 3: 경계 대기)가 이 몫을 겨누지만 2.1 ms 로 3 ms 기준 미만이라 새 이슈를 만들지 않는다.

### 3-4. 호스트·eager (이슈 본문 후보 2, #40 경로)

- 입력 준비·메타데이터 빌더 eager 는 +0.10 ms, 검증 뒤처리 eager 는 +0.07 ms 다. 호스트 유휴와 잔틈은 변화가 없다.
- 증가분의 90 % 가 타깃 포워드 CUDA 그래프 안의 GPU 시간이다.
- #40 커널 켜짐 r2/r3 의 75 ms 는 같은 토큰 웨이브였다(계획 1 장). #40 경로의 동시 2 몫은 이 표에서 0.1 ms 미만이다.

### 3-5. 산문

- K4 는 같은 프롬프트·같은 스텝이었지만 192 자(약 14 스텝)에서 텍스트가 갈라졌다. 39 스텝 평균의 MoE 호출당 시간(672 µs)은 같은 토큰(553)과 다른 토큰(791) 사이다.
- 비프로파일 산문 `[A, A]` 91.7 ms, `[A, B]` 95.8 ms 로, 산문도 코드와 같은 경로이고 빠른 모드가 없다.
- 산문 c1 스텝(68.3 ms, 청크 간격 중앙값)은 코드 c1 과 같다.

## 4. 판단과 인계

- **새 이슈 제안 없음.** 몫 ≥ 3 ms 인 항목은 MoE 라우팅 몫 15.4 ms 뿐이고, 서로 다른 전문가마다 가중치를 읽는 비용이다. 오너 보류 결정(EP #16, b12x MoE #31)의 판단 자료로만 남긴다. 이 데이터만으로는 EP 가 이 몫을 줄인다고 볼 근거가 없다(랭크당 읽는 바이트의 평균은 같다). 필요하면 서로 다른 프롬프트 동시 2 로 따로 재야 한다.
- **#42 인계:**
    - 동시 ≥ 2 디코드 벤치는 서로 다른 프롬프트로 정의한다(한 요청 `[A, B]` 또는 서로 다른 프롬프트 요청). decodebench 의 같은 프롬프트 동시 2 는 도착 타이밍에 따라 75/93 ms 로 이봉이라 쓰지 않는다. 서로 다른 프롬프트도 같은 스텝 여부에 따라 92~96 ms 로 흔들리니 첫 토큰 간격을 함께 기록한다(`decodebench_i41.py` 의 `first_offset_ms`).
    - SGLang 의 +4 ms 는 TTFT 가 +0.27 s 늘었는데 두 스트림 속도 차는 0.08 tok/s 라 정렬 여부를 가릴 수 없다. 서로 다른 프롬프트로 재측정하기 전에는 목표로 쓰지 않는다.
    - 9/14 보고서의 "동시 2 격차 = 호스트 지문" 문장은 2-1·2-2 표로 정정한다.
- **#39 인계:** 동시 ≥ 2 에 효과를 주장하는 코드 수정 A/B 는 서로 다른 프롬프트로 잰다. 호스트·eager 범주는 동시 2 증가분이 0.2 ms 미만이라 그쪽 수정은 동시 2 격차를 줄이지 못한다.
