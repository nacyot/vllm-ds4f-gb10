메타 이슈 #43 마감: 다섯 주제가 어떻게 끝났나

2026-09-15 오전에 "DS4.1F 포크에서 지금 풀어야 할 다섯 주제" 를 적었다. 하루 뒤인 2026-09-16, 그 다섯 주제가 모두 끝났다. 이 글은 각 주제가 무엇을 물었고 무엇으로 답했는지를 정리한 마감 기록이다.

결과부터: 다섯 주제 열두 건이 전부 닫혔고, 열린 채로 남은 것은 API 프런트엔드 배치(#29) 하나뿐이다. 오너가 최종 배포 때 하기로 정했다. 프로덕션 최종 기준선 prod-final 을 SGLang 대비로 환산하면 산문 94.4, 코드 94 대 97, 128K 프리필 80.1, 에이전트 작업 속도 102.3 으로 다섯 항목 모두 원 목표 범위에 들었다.

얼마나 달라졌나를 먼저 보면 이렇다. 왼쪽이 이슈를 쓰던 2026-09-15 오전의 값(fork0914), 오른쪽이 2026-09-16 최종 기준선(prod-final)이다.

세 번째 줄에 주의가 필요하다. 헤드 여유는 코드로 만든 차이가 아니라 시작 메모리 상태가 달라서 생긴 차이이기도 하다. 값을 그대로 성과로 읽지 않는 게 맞다.

1. 디코드 스텝 격차

같은 vLLM 코어인데 우리 스텝이 75.9 ms, T2W 기본 설정이 68.0 ms, SGLang 이 65.4 ms 였다. 스텝당 통과 토큰은 셋 다 5.82 로 같았으니 순수하게 스텝이 느린 것이었다. 세 갈래로 나눠 물었다.

갈래당시지금

원인은 콜드 NVMe 읽기였다

디코드 스텝마다 러너가 해시를 GPU 에서 내려받은 뒤 Engram 표 두 장을 직렬로 기다렸다. 그 표의 페이지가 디스크에서 갓 읽히는 콜드 페이지다. 샤드 상주율이 0.1 %, 표 하나가 72~96 페이지, 장치가 초당 22,000 IOPS 이니 기다림이 길 수밖에 없다. 그동안 GPU 는 스텝당 5.6 ms 를 놀았다.

고친 방법은 순서를 바꾼 것이다. 레이어 1 표만 기다리고 레이어 14 표는 포워드가 도는 동안 배경에서 채운다(ENGRAM_DECODE_ASYNC=1, ENGRAM_CHUNK_RUNS=8).

기준선73.3 / 70.2 / 68.4 ms70.3 / 70.7 ms5.6 ms

수락 길이 5.82 는 그대로고 158K 니들도 콜드와 후속 턴 모두 정답이었다.

표 두 장을 모두 배경으로 돌리는 모드도 만들어 봤다. 코드는 64.6 ms 로 더 빠른데 산문이 3.7 ms 느려진다. 산문에서는 레이어 1 조회가 콜드 페이지를 GPU 제자리 fault 로 읽기 때문이다. 코드는 n-gram 반복 덕에 페이지가 이미 올라와 있어 fault 가 없다. 워크로드에 따라 갈리므로 옵트인으로 남겼다.

업스트림 커널은 값이 없었다

업스트림 vLLM PR 56562 에서 token_to_req_indices 커널만 떼어 이식하고 기본 꺼짐으로 게이트한 뒤 A/B 했다. 코드 c1 평균 스텝 개선이 0.304 % 였다. 채택선 2.7 % 에 한참 못 미쳐 코드를 되돌렸다. 정확성 자체는 문제가 없었다(경계 케이스 36 건 통과). 효과가 없다는 것을 확인한 것이 결과다.

동시 2 의 증가분은 MoE 라우팅이다

요청이 하나에서 둘로 늘 때 우리는 27 ms 가 느는데 SGLang 은 4 ms 만 늘었다. 4 랭크 프로파일 다섯 종을 떠서 증가분 전부를 범주에 배분했다.

먼저 밝혀진 것은 증가분이 두 값 사이를 오간다는 점이다. 두 스트림이 같은 토큰을 디코드하면 +7.3 ms, 다른 토큰이면 +26.4 ms 다. 같은 프롬프트로 두 요청을 보내도 대개 한 스텝씩 어긋나므로 벤치에서는 큰 쪽이 잡힌다.

큰 쪽 26.4 ms 의 내역이다.

MoE 19.78 ms 중 15.42 ms 는 순수한 라우팅 몫이다. 두 토큰이 서로 다른 전문가로 가면 커널이 읽어야 할 가중치 블록이 늘어난다. 호스트 쪽은 전부 0.2 ms 미만이었다. 2026-09-14 보고서가 이 격차를 "호스트 지문" 으로 추정했는데 그 추정은 틀렸다.

3 ms 를 넘는 몫이 MoE 라우팅 하나뿐이고, 그것은 국소 수정으로 없앨 수 있는 성질이 아니다. 그래서 후속 이슈를 만들지 않았다.

2. 프리필 격차

128K 콜드 프리필이 우리 1,359 tok/s, T2W 2,034, SGLang 2,102 였다.

갈래당시지금
인덱서 TP 분할 이식 (#38)미적용채택, S128 +22 ~ 23 %
프리필 커널 후속 (#17)병목 미상청크의 26 % 가 랭크 불균형, 그 73 % 가 Engram 조회

지금 prod-final 은 S128 첫 회 1,683.7 tok/s 다. 세 회차가 1,598.9 에서 1,683.7 사이로 흔들린다. 32K 는 1,880.9 tok/s, 긴 세션 158.5K 콜드는 1,933.6 tok/s 로 SGLang 의 98 % 까지 왔다.

인덱서 분할이 가장 큰 한 방이었다

T2W 의 인덱서 프리필 TP 분할을 우리 트리로 옮겼다. 같은 빌드에서 게이트만 바꿔 잰 A/B 에서 S128 이 22.41 %, 23.11 % 늘었다. prefault 를 끄든 켜든 양쪽에서 같은 방향이었다. 32K 에서는 개선이 확인되지 않았다.

랭크마다 설정이 어긋나면 조용히 이상해지는 대신 기동을 거부하게 했다. 워커 한 대만 값을 다르게 두고 띄우니 시작 58 초 뒤 가중치 로드 전에 네 랭크가 같은 줄로 죽었고 교착은 없었다.

동일성 검증은 비트 비교로 할 수 없었다. 분할을 켜지 않아도 같은 프롬프트 재실행이 비트 단위로 같지 않기 때문이다. top_k_per_row_prefill 의 행 안 순서가 회차마다 달라진다. 8K 프롬프트는 첫 토큰이 거의 동점이라(logprob 차 0.3 nats 안) 판정에 쓸 수 없었고, 32K 는 네 번 중 세 번이 같은 텍스트였다. 그래서 GPU 커널 수준의 동일성으로 판정했다.

남은 프리필 시간은 어디 있나

128K 청크 하나가 2,224.5 ms 다. 이것을 네 랭크에서 뜯었다.

가장 큰 발견은 청크 시간의 26 %(583 ms)가 랭크 불균형 대기이고, 그중 73 %(425 ms)가 Engram 조회 커널의 랭크 차라는 것이다. 조회 시간이 랭크마다 46, 144, 328, 468 ms 로 벌어진다. 표당 페이지 수(26,000 에서 44,000)보다 훨씬 가파르게 늘고, 다음 청크 프리페치와 겹칠 때 약 두 배가 된다.

mHC tilelang 커널 세 개는 의심을 벗었다. 대역폭 하한의 1.24 ~ 1.37 배로 이미 충분히 빠르다. 하한까지 줄여도 청크당 68 ms, GEMM 패스를 융합으로 아예 없애도 66.4 ms 로 3 % 판정선(66.7 ms)에 걸린다. 여기는 손댈 값이 없다. 코드 변경 0 이다.

Engram 조회 쪽은 레버를 만들어 봤다. 다음 청크 프리페치를 이번 스텝 조회가 GPU 에서 끝난 뒤로 미루는 것이다. 프로파일에서는 잘 들었다(랭크 3 조회 468 → 255 ms, 불균형 손실 583 → 440 ms, 청크 창 5.9 % 단축). 그런데 프로파일러를 끄고 S128 로 재니 1,733 대 1,737 tok/s 로 차이가 없었다. 되돌렸다.

여기서 방법론 문제가 드러났다. S128 회차 편차가 1,625 에서 1,942 tok/s 로 ±8 % 다. 매 회차 헤드에서 스왑과 직접 회수, 컴팩션이 일어난다. 이 잡음이 청크당 6 % 짜리 이득을 세 회 평균으로는 가릴 만큼 크다. 편차를 줄인 프로토콜로 다시 판정하는 일을 #44 에 파킹했다.

첫 시도는 효과가 0 이었다

이 작업에서 기록할 값어치가 있는 것은 첫 부팅이 아무 효과가 없었다는 사실이다. 예약을 4,096 토큰 걸었는데 대기가 64.96 / 66.73 초로 기준선과 똑같았다. 한 토큰도 물리지 않았다.

원인은 프리필 청크를 묶는 상한이 토큰 예산이 아니라 입력 예산에서 드래프트 슬롯을 뺀 값이었다는 것이다. dspark 드래프터가 요청마다 슬롯 4 개를 가져가고, 스케줄되는 요청은 입력 예산에서 새 토큰 수와 슬롯 수를 함께 뺀다. 프리필 청크가 4,092 토큰을 받아 입력 예산을 0 으로 만들면 대기 루프가 즉시 빠져나가 짧은 요청이 입장하지 못한다. 토큰 예산에서만 빼 봤자 상한을 고르는 min() 이 여전히 입력 예산 쪽을 골랐다.

두 예산 모두에서 자르도록 고치자 같은 부팅 조건에서 7.01 / 8.71 초가 나왔다. 이 실수를 그대로 재현하는 단위 테스트를 남겼다.

검증 중에 실제 결함 두 개가 나와 그 자리에서 고쳤다. 첫째, 워커를 재부팅하면 /mnt/kvdisk NFS 마운트가 돌아오지 않아 랭크 3 의 디렉터리 생성이 실패하고 start limit 에 걸려 서버가 약 16 분 내려갔다. fs 티어 디렉터리를 랭크 0 에서만 만들게 고쳤다. 마운트를 부팅 때 복원할지는 오너 결정이라 #45 에 남겼다. 둘째, 생각하기 모드 요청의 첫 토큰이 다른 필드로 와서 웜업이 실패로 기록하던 것을 고쳤다.

대시보드가 프리필을 잘못 세고 있었다

Grafana 프리필 패널이 KV 복원까지 프리필 토큰으로 세고 있었다. 분자를 실제 계산 토큰 기준으로 바꿨다. 재기동도 설정 변경도 없었고 엔진 코드 변경 0 이다.

첫 배포 때 붙였던 설명도 틀린 것이어서 고쳤다. "복원 요청은 복원 시간이 분모에 들어가 낮게 보인다" 고 적었는데, 실제로는 복원 대기가 큐 시간으로 잡혀 분모에 거의 들어가지 않는다. 493K 복원 한 번에서 TTFT 8.6 초 중 0.49 초였다.

1,045,649 파일 전부 일치, 불일치 0, 삭제 0 이다. 약 10 분에 초당 170 MiB 로 읽었다. 스크립트는 기본이 보고 모드이고, 서버 상태가 불확실하면 삭제를 거부하며, 삭제 직전에 분류와 파일 identity 를 다시 본다. 실제 삭제는 서버가 내려간 창에서만 한다.
