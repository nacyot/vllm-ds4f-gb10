## 1. 결론

- **128K 청크(문맥 102K~123K, 6 개)의 벽시계는 2,224.5 ms** 다. 3 % 기준 T 는 66.7 ms 다.
- 분해하면 커널 합이 약 1,480 ms, NCCL 전송 224 ms(10.1 %), 랭크별 NCCL 대기 106~505 ms, 호스트 쪽(프리폴트 대기 17~31 ms, 그 밖의 유휴 4~7 ms, 잔틈 3 ms)이다(2-1).
- NCCL 호출 116 회를 4 랭크에서 호출 단위로 맞추면 **청크당 불균형 손실이 583 ms(창의 26 %)** 다. 그중 **425 ms 가 Engram 조회 커널의 랭크 차**이고, 나머지는 어텐션 +65, 인덱서 +38, MoE +24 ms 의 호출별 흔들림이다(2-4).
- **(a) mHC 3 커널:** 4,092 토큰 호출당 1.72 / 0.84 / 1.06 ms 로 대역폭 하한의 1.24~1.37 배다. 하한까지 줄여도 청크당 68 ms, GEMM 패스를 융합으로 없애는 상한은 66.4 ms 로 T 미만이다. **코드 변경 없음.**
- **(b) Engram 조회:** 청크당 r0 46 / r1 144 / r2 328 / r3 468 ms 다. 표당 페이지(26K / 36K / 42K / 44K)보다 훨씬 가파르게 늘고, 다음 청크 프리페치 populate 와 겹칠 때 최대 약 2 배가 된다(2-3, 3 장). U ≈ 425 ms 로 T 를 넘어 레버를 구현했다(4 장).
- **(b) 레버 `DSV41_ENGRAM_PREFETCH_AFTER_LOOKUP`:** 다음 청크 populate 를 이번 스텝의 조회가 GPU 에서 끝난 뒤로 미룬다.
    - 켜짐 프로파일(문맥 110K~123K): 조회 r3 468 → 255 ms, 손실 583 → 440 ms, 창 2,224 → 2,073 ms(같은 문맥 4 청크끼리 −5.9 %).
    - 비프로파일 S128 r2~r4 평균: 켜짐 1,733, 꺼짐 1,737 tok/s(−0.2 %). 채택선(+3 %, ≥ 1,836)에 못 미쳐 **채택하지 않고 되돌렸다**(`2161dfc97f`, 노드 4 대 반영).
- **(c) NCCL 대기:** 원천은 (b) 가 73 % 다. 나머지는 특정 랭크가 아니라 호출마다 늦는 랭크가 바뀌는 커널 흔들림이라 이 이슈의 레버가 없다.
- 두 부팅 모두 S128 회차 간 편차가 1,625~1,942 tok/s(±8 %)였다. 매 회차 헤드에서 스왑·직접 회수·컴팩션이 있었고, 이 편차가 청크당 약 6 % 의 이득을 3 회 평균으로는 가를 수 없게 만든다(5 장). #43 에 넘긴다.

## 4. (b) 레버: Engram 조회 게이트

### 4-1. 레버 선택 과정

- **서버 정지 창의 마이크로벤치(27c4, `engram_lookup_bench_i17.py.txt`, 기록 `implement-lookup-bench_i17.jsonl`).** 실표 두 개에 랭크별 페이지 수를 맞춘 행으로 네 조건을 비교했다: 현재 커널, 행 id 정렬(프로그램마다 연속 구간), 정렬 + 현재 보폭, 그리드 1/4. 각각 동시 프리페치 유무를 곁들였다.
    - 1 차 실행은 무효다. 제 정렬 커널이 int32 행 id 로 오프셋을 계산해 넘쳤고, 틀린 주소를 읽어 rank 0 조건에서 illegal memory access 로 끝났다(프로세스만 종료, GPU 정상 확인).
    - 고친 2 차 실행은 모든 변형이 base 와 비트 동일했다. 그러나 같은 조건 안에서도 69~685 ms 로 흔들렸다. 측정 사이 CPU populate 동안 GPU 가 유휴라 클럭이 305 MHz 로 내려가는 인공 효과로 보고, 판정에 쓰지 않았다.
- 그래서 **프로덕션 트레이스의 증거(3 장 P12 비교, 2-3 의 겹침 구조)로 경합 제거를 레버로 골랐다.** 정렬 접근(TLB 지역성)은 입증하지 못해 구현하지 않았다.

- 노브: `DSV41_ENGRAM_PREFETCH_AFTER_LOOKUP`(dsv41.env 기본 0, ctl KNOBS). 켜지면 랭크마다 로그 한 줄을 남긴다.

    - 새 `test_mmap_table_prefetch_waits_for_lookups` 와 게이트를 단 `test_engram_mmap_matches_resident`(tp 1, 4)는 통과했다.
- pre-commit 은 ruff check·format, typos, shellcheck 통과다. mypy-3.10(`os.posix_fadvise` 가 darwin 스텁에 없음)과 `check-torch-cuda-call`(시험 파일의 기존 `torch.cuda.synchronize`) 실패는 기존 코드라 커밋 때 두 훅만 SKIP 했다.

## 5. 해석

- **기전은 확인됐다.** 게이트로 populate 가 조회와 겹치지 않자 페이지 많은 랭크의 조회가 크게 줄었다(r3 −45 %). 늦은 랭크 대기의 Engram 원천이 425 → 249 ms 로 줄었고, 같은 문맥 청크 창이 5.9 % 줄었다. 어텐션·인덱서·MoE 원천이 조금 늘어난 것은 가장 느린 원천이 줄자 다음 흔들림이 드러난 것으로 본다.
- **S128 에서는 보이지 않았다.** 두 부팅 모두 비프로파일 회차가 1,625~1,913 tok/s 로 퍼졌다.
    - 헤드는 매 회차 직접 회수·컴팩션이 있었다(꺼짐 r3·r4 allocstall 20~47, 켜짐 r2 스왑아웃 58 만 페이지, r4 컴팩션 336).
    - 꺼짐 r2 는 1 초 해상도 로그에서 청크 간격이 전반적으로 길고(평균 2.45 s, r1 약 2.14 s) 3.6 s 정지가 한 번 있었다.
    - 이 편차는 청크당 약 6 % 이득보다 커서, 회차 3 개 평균으로는 채택선을 가를 수 없다. 켜짐 쪽이 실제로 효과가 없다고 결론 내릴 근거도 없다.
- **프로파일러 부풀림:** P12 요청 전체의 토큰당 시간이 같은 상태의 비프로파일 12K(`i17-base-S12r2`)보다 4.8 % 길다(계획 한계 5 % 안). 계획의 10 초 통계 비교는 쓸 수 없었다. vLLM 통계가 prompt 토큰을 요청 첫 토큰 시점에 한꺼번에 세기 때문이다(`vllm/v1/metrics/stats.py:455-469`, 128K 완료 창에 12,780 tok/s). P128 요청 wall 70.8 s 는 비프로파일 S128 범위(66.8~78.1 s) 안이다.
