# #39 결과 — 같은 빌드의 게이트별 몫과 S128 회차 비교

## 결론

- **네 부팅 × 8셀, 전부 성공.** casebench 28행과 decode 24행을 중복·누락 없이 얻었다. 부팅 재시도, 셀 실패, 메모리 skip은 없다.
- **분할은 S128에서 +22.41% / +23.11%.** prefault 꺼짐·켜짐 두 조건 모두 개선했다. S32에서는 −2.92% / −0.49%로 개선을 확인하지 못했다.
- **prefault는 코드 c1 스텝을 3.511 / 1.098 ms 줄였다.** 개선 방향은 같지만 분할 상태에 따라 관측 몫이 달랐다.
- **SSOT의 순서 판정은 회차 편차.** r4−mean(r2,r3)의 부호가 A/B/C는 양수, D는 음수여서 네 구성 공통의 순서 효과 기준을 충족하지 않는다.
- 마지막 D는 knob 없는 start였다. 네 노드 override 0 bytes·Environment 공백·dirty 0, health 200, ATTENTION 없음으로 복구했고 **04:41:13 KST에 watchdog timer를 start하여 active를 확인**했다.

실행일은 2026-09-16, 시각은 모두 KST. 정본은 [#39 코멘트 icmt-c6218ef6 사본](ssot-comment.txt)이며 [승인 계획](plan.md)을 따랐다. 실행·집계·문서화에 Codex의 AI 지원을 사용했다.

## 구성별 측정값

각 부팅에서 warm → warm2 → S128 r1/r2/r3 → S32 → decode(prose,code × c1/c2/c4) → S128 r4 순서로 [run-cell.sh](run-cell.sh)를 한 번씩 호출했다. SSH 호출은 셀별 전경이며 다음 셀은 이전 셀 종료와 rc·새 행·health·ATTENTION을 확인한 뒤 실행했다.

전체 셀 기록은 [i39.log](i39.log), 원본 결과는 [casebench.jsonl](casebench.jsonl), [decode.jsonl](decode.jsonl)에 있다. 태그를 바꾸거나 실패 행을 대체하지 않았다. 모든 S128 직전 메모리가 3.0 GiB 이상이어서 대기/skip은 없었다. 메모리 최저는 기존 casebench 샘플과 경계 관측에 기반하며, 부팅·디코드 전체를 연속 샘플링한 최저라는 뜻은 아니다.

**부호가 + / + / + / −로 흩어졌다. SSOT 규칙에 따라 회차 편차로 판정한다.** A/B/C에서는 뒤가 빨랐고 D는 −1.40%였다. 네 구성 공통의 후반 저하를 재현하지 못했으며, 이 짧은 프로토콜로 #46의 22분 연속 스위트 이후 하락 원인까지 확정할 수는 없다.

다른 운영 타이머는 그대로 유지했다. [journal 기록](tools-postflight.txt)에 따르면 KV GC가 04:02:18~04:19:55 실행되어 A decode/r4, B 전 셀, C 부팅과 겹쳤다. 04:32:19에 다시 시작한 GC는 종료 수집 시에도 진행 중이라 D 부팅 끝과 전 셀에 겹쳤다. C 측정 셀은 두 GC 실행 사이였다. 이 비대칭과 구성별 메모리 상태·회차 변동 때문에 이번 몫은 해당 운영 조건에서의 관측값이다. GC를 중지하거나 재측정으로 값을 고르지 않았다.
